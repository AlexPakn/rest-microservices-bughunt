# Оценка задания и дальнейшие действия

## Оценка

Это практическая работа средней сложности: код небольшой, но требуется доказать ошибки,
согласовать поведение трёх сервисов и правильно оформить историю исправлений.
Основная сложность — авторизация и обработка отказов соседних сервисов.
Ориентир при самостоятельном выполнении с нуля: 6–10 часов для знакомого с Python и Git,
1–2 рабочих дня при первом знакомстве с FastAPI, pytest и pull request.
Это оценка объёма задания, а не обещание времени оставшейся работы.

В условии есть противоречие: pytest-тесты обязательны в разделе «Завдання»,
а в критериях названы необязательными. Подготовлен вариант с тестами.
Условие не задаёт число багов, точный REST-контракт и формат отчёта;
выбранные решения и ограничения зафиксированы в документации.

При копировании испортились кавычки, отступы, дефисы аргументов Uvicorn,
YAML и появились Markdown-экранирования. Это исправлено **до** создания baseline,
чтобы измерять смысловые дефекты работающих сервисов. Исходный текст сохранён отдельно.

ошибками тестов они не являются. Основные зависимости сохранены как в условии,
но их транзитивные зависимости не зафиксированы полностью: среда не является полным lockfile.

## Что осталось со стороны владельца

Для запрошенного результата — GitHub и отчёт со скриншотами — дополнительных действий не нужно.
Можно передавать преподавателю ссылки из [GITHUB_SUBMISSION.md](GITHUB_SUBMISSION.md).
Все 13 PR оставлены открытыми, чтобы отдельные исправления было удобно проверить.

Отчёт `BUG_REPORT.md` содержит 15 встроенных PNG. Это снимки HTML-страниц с дословным
выводом реальных запусков pytest; исходные тексты и команды также доступны в GitHub.

Если позднее понадобится контейнерная проверка, нужен Docker Desktop с Compose;
команды есть в README. Если понадобится титульный лист, DOCX/PDF или особая форма сдачи,
потребуются требования преподавателя, ФИО и группа. Сейчас отчёт опубликован в Markdown.

## Что ещё учитывать

PR подготовлены последовательно: следующий сравнивается с предыдущей fix-веткой.
Так в каждом PR виден ровно один новый патч. Это обычная цепочка зависимых PR;
перед объединением следующего PR его базу меняют на `main`, когда предыдущий уже объединён.
Если преподаватель требует все PR строго к исходному `main` независимо друг от друга,
нужно сначала уточнить это требование: текущие исправления частично зависят друг от друга.

Нельзя считать систему готовой к реальной продаже товаров: состояние в памяти,
демонстрационные пароли и отсутствие резервирования остатков явно описаны в README.
Это учебный стенд для поиска ошибок REST-интеграции.
